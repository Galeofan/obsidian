## 1. Цель
Реализовать функционал автоматической загрузки и первичной регистрации:
- **Юридических лиц (legal_entity)**
- **Торгово‑сервисных предприятий (merchant / ТСП)**
на основании входящих CSV‑файлов, получаемых с FTP, с фиксацией истории обработки файлов и построчных ошибок.

---

## 2. Источник и формат данных

### FTP
- Входящие директории:
  - `/in/legal_entity/`
  - `/in/merchant/`
- Маски файлов (без учёта регистра):
  - `LEGAL_ENTITY_*.csv`
  - `MERCHANT_*.csv`
- После обработки файл перемещается:
  - в `processed/` при успехе
  - в `failed/` при ошибке
- При совпадении имени файла в `processed/` — добавляется timestamp.

### CSV
- Кодировка: **UTF‑8**
- Разделитель: `;`
- Header: **обязателен**
- Кавычки и экранирование: **разрешены**
- Пустые строки: **недопустимы**
- Частично пустые колонки: **допустимы**
- Все колонки, заданные в шаблоне, считаются **обязательными** (пустота = ошибка валидации).

---

## 3. Шаблоны файлов

- Используются **2 отдельных шаблона**, зафиксированных в коде:
  - `legal_entity.csv`
  - `merchant.csv`
- Шаблоны определяют:
  - список колонок,
  - порядок,
  - обязательность,
  - маппинг в поля БД.

### Ключевые поля
- `acquirer_entity_id` — `varchar`, **без лидирующих нулей**
- `acquirer_merchant_id` — `varchar`, **без лидирующих нулей**

---

## 4. Идемпотентность и ключи

### legal_entity
- Уникальный ключ: `acquirer_entity_id`
- Поведение при дубле: **SKIP**
- UPSERT: **нет**

### merchant
- Уникальный ключ: `(acquirer_merchant_id, legal_entity_id)`
- Поведение при дубле: **SKIP**
- UPSERT: **нет**

### Повторная загрузка файлов
- Допускается
- Ранее загруженные строки пропускаются по ключам

---

## 5. Связь merchant → legal_entity

- Связь по **внутреннему `legal_entity_id`**
- Если `legal_entity` не найден:
  - строка считается **ошибочной**
  - автосоздание **запрещено**
  - строка **не пропускается**, а фиксируется как invalid

---

## 6. Таблица реестра файлов

Хранит **метаданные и статус обработки**, без хранения контента файла.

### Основные поля
- `id`
- `file_name`
- `status`
- `upload_date`
- `updated_date`
- `lines_count`
- `lines_valid`
- `lines_invalid`
- `lines_skipped`
- `created_by = 'PHUB'`
- `updated_by = 'PHUB'`

### Статусы
```
UPLOADED
PARSING
PARSED
VERIFYING
VERIFIED
PROCESSING
COMPLETED
COMPLETED_WITH_ERRORS
FAILED
```

- `COMPLETED_WITH_ERRORS` — файл обработан, но есть `lines_invalid > 0`.

---

## 7. Таблица ошибок по строкам

Хранит детальную информацию о каждой ошибке.

### Обязательные поля
- `file_id`
- `line_no`
- `entity_type` (LEGAL_ENTITY / MERCHANT)
- `error_code`
- `error_message`
- `raw_line`
- `created_at`

- Хранение распарсенных значений (json) **не требуется**.

---

## 8. Обработка файла (pipeline)

1. Polling FTP входной директории
2. Файл найден → запись в реестр (`UPLOADED`)
3. Скачивание файла
4. `PARSING` → построчное чтение CSV
5. Валидация строк
6. `PROCESSING`:
   - insert в `legal_entity` / `merchant`
   - `ON CONFLICT DO NOTHING`
7. Подсчёт статистики строк
8. Установка финального статуса:
   - `COMPLETED`
   - `COMPLETED_WITH_ERRORS`
   - `FAILED`
9. Перемещение файла в `processed/` или `failed/`
10. Публикация отчёта на FTP (механизм уже существует)

---

## 9. Транзакционность и объёмы

- Ожидаемый размер: **тысячи строк**
- Допустимо:
  - одна транзакция на файл
  - или батчи
- Критичных требований к изоляции нет

---

## 10. Запуск и управление

- Обработка запускается **автоматически при появлении файла**
- REST‑endpoint’ы:
  - для ручного запуска — **не нужны**
  - для просмотра статуса — **не нужны**
- Дальнейшая регистрация ЮЛ/ТСП выполняется **уже существующими шедулерами**

---

## 11. Аудит и логирование

- Все записи создаются от пользователя **PHUB**
- Логи:
  - по файлу (file_id, имя, итоговая статистика)
  - по ошибкам строк (line_no, error_code)
